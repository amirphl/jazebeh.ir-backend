# Staging deployment

Staging is a separate Ubuntu 24.04 server. Do not share its Compose containers, volumes, database, Redis, credentials or customer data with production. Point `staging.jazebeh.ir` at the server and install the existing wildcard certificate under `/etc/letsencrypt/live/`; set `STAGING_CERT_NAME` to that certificate directory name.

Run `./scripts/prepare-staging-host.sh`, provide a `yamata-frontend-beta` image, and copy `config/staging.env.example` to `.env.staging`. Replace each `CHANGE_ME` value with a unique staging secret and set `PGADMIN_LISTEN_BIND_IP` to a real, non-loopback IPv4 address on the staging host; deployment rejects `127.0.0.1` and `0.0.0.0`. Provision the three pgAdmin secret files named in the env file, ensuring the deployment user can read them and the container users can read the password and htpasswd files. Keep these files and `.env.staging` private. Do not copy production data, keys or DSNs.

```sh
./scripts/deploy-staging-beta.sh --domain staging.jazebeh.ir
```

The deployment uses `docker-compose.beta.yml` with `docker-compose.staging.yml`, its own `yamata-staging` project and volumes, smaller PostgreSQL settings, and a separate campaign-scheduler container. It refuses to replace existing non-staging app, scheduler, PostgreSQL or Redis containers. It requires an empty, untracked database on first deployment and maintains a staging migration tracker. Once a failed migration's SQL/data issue has been corrected, rerun the deployment; it retries that migration before later files and inserts missing mock fixtures without overwriting existing rows. Back up staging data before upgrading; the deployment does not delete volumes.

The frontend is at `/`, the API is under `/api/`, short links under `/s/`, Grafana under `/grafana/`, and GlitchTip under `/sentry/`. Access pgAdmin at `https://staging.jazebeh.ir:14433/pgadmin/` through its separate authenticated proxy, reachable only on `PGADMIN_LISTEN_BIND_IP`; the main HTTPS listener does not expose it. GlitchTip works without an application DSN initially. After creating a staging project, copy its DSN into `.env.staging` but replace only its public origin with the internal endpoint: for example, convert `https://<key>@staging.jazebeh.ir/sentry/<project-id>` to `http://<key>@sentry-beta:8000/sentry/<project-id>`. Do not use the public hostname inside containers: the staging network has no public egress. Redeploy to forward application and Nginx errors; deployment submits a probe event when `SENTRY_DSN` is configured. `BASE_PATH=/sentry` configures GlitchTip for this URL. DNS and the certificate must cover `staging.jazebeh.ir`; nested subdomains are not required.

Inspect status with `docker compose -p yamata-staging --env-file .env.staging -f docker-compose.beta.yml -f docker-compose.staging.yml ps` and logs with the same command followed by `logs`. Mock operations use isolated staging state and can still trigger status processing, notifications, accounting and refunds. Do not use a production dataset. Resource limits are conservative starting points and must be monitored under actual staging workloads.

The total configured container memory ceilings are below the server's 8 GiB, leaving room for the host, filesystem cache and Docker. These ceilings are not workload guarantees: monitor out-of-memory events and actual load, and resize or use a larger host if services cannot start or a test workload exceeds them.

Simulated OTPs are stored in `/data/mock-otp.jsonl` inside `yamata-app-beta` (mode 0600), not in logs. Only trusted staging operators should read this sensitive outbox with `docker exec`.

Before the first staging deployment, replace `MOCK_SEED_ADMIN_PASSWORD`, set `ADMIN_2FA_MOBILES=stageadmin:989100000000` (or use the selected `MOCK_SEED_ADMIN_USERNAME`), and deploy. The fixture seeder creates this `superadmin` exactly once and does not rotate its password on deployment retries. Use a staging-only test mobile in `989...` format. Captcha and mock OTP verification remain enabled; only trusted operators may read the OTP outbox. Changing the mapping requires redeployment to reach the application container.

The seeder also preserves an existing bot's password and active state. The campaign worker requires the configured `BOT_PASSWORD` to match the stored bot password; coordinate any credential rotation explicitly before redeployment.

The separately supplied frontend must recognize mock Atipay tokens and avoid sending users to the real payment gateway. The backend cannot enforce browser navigation, and this repository does not include a mock gateway UI. The staging overlay makes its application network internal and deployment verifies that both backend containers cannot reach a public IP. This is defense in depth for Go clients with custom transports and non-Go processes; retain host-level egress controls if the stack is later attached to an egress-capable network.

Run `APP_ENV=staging EXTERNAL_SERVICES_MODE=mock ./scripts/verify-staging-observability.sh` after deployment to inspect container ownership, health and Prometheus targets. The separate `yamata_campaign_scheduler` target exposes mock campaign-send/status metrics on its internal port `9091`; the app target continues to expose API, OTP, payment, short-link, and OpenAI mock metrics. Run `./scripts/verify-staging-no-external-egress.sh` to repeat the deployment egress check, and `./scripts/verify-build-proxy.sh yamata-no-orochi-staging` against the built image to check its configuration and history. These checks do not prove the absence of every possible secret. The staging GlitchTip tag is pinned to 6.2.2, but a tag is not an immutable digest; pin an approved digest before relying on reproducible deployments.

Production-only operational tools now require `APP_ENV=production`; live publishing requires their explicit `--execute` option, and restore requires `--confirm-production-restore`. Existing production automation must be updated accordingly. The Dockerfile no longer persists proxy variables; production deployments needing a runtime proxy must explicitly configure it in their runtime environment.

For the production reference-data importer, use `sudo env APP_ENV=production EXTERNAL_SERVICES_MODE=live ... --confirm-maintenance-window` so `sudo` passes the environment to the launcher. Its transient service receives these environment settings explicitly. This import is production-only and should never use staging data or containers.
